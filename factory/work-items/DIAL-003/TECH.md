# DIAL-003 — technical proposal

## Architecture and prerequisite

Extend the existing inline player controller and both MCP UI resources. Each iframe retains its own `HTMLAudioElement` and selected station. A versioned `BroadcastChannel` carries transient owner announcements, status requests, transfer requests, Pause requests, and acknowledgments. A **single named exclusive Web Lock**, held throughout buffering and playback, gates every call that can start audio. Broadcast messages alone do not establish exclusion. The [Web Locks specification](https://www.w3.org/TR/web-locks/) defines exclusive lock and abortable waiting; the [Broadcast Channel API](https://developer.mozilla.org/en-US/docs/Web/API/Broadcast_Channel_API) is scoped to the same origin and storage partition. The actual ChatGPT iframe origin, partition, API exposure, lifecycle, and user-activation behavior remain unproven and are the first implementation gate.

The gate uses a small, explicitly versioned probe build of the existing MCP UI resources on an authorized test endpoint. With both real ChatGPT thread frames open simultaneously: exchange random probe nonces both ways; hold the proposed lock in A and show B cannot acquire it; reverse; close/remount a holder and show recovery; test background delivery and a user-clicked transfer followed by `audio.play()`. A mere `navigator.locks` property check or same-origin string comparison is insufficient. Save timestamped observations and probe code/resource revision. If any prerequisite fails, stop before integrating the feature and send the evidence to Foreman for a revised spec. No server fallback is authorized by this document.

## Ownership protocol

- Use a stable protocol version and namespaced channel/lock names shared by both DIAL resources. A frame gets a random ephemeral instance ID and increments a local attempt ID for every Play, Pause, selection, or teardown. Messages include version, sender, request ID, owner attempt/epoch, type, and bounded status fields. Never broadcast stream URLs, click tokens, account data, or arbitrary HTML. Validate message shape/version and ignore self, duplicates, and stale acknowledgments.
- On Play, create a cancelable pending attempt, announce a transfer request, and request the exclusive lock with an `AbortSignal` and finite timeout. An active holder handles the transfer by invalidating its play attempt, calling `audio.pause()` synchronously, updating its visible state, then resolving its lock-holding promise. It acknowledges only after pausing. A pending contender may resend its transfer request or respond to a newly announced holder, so near-simultaneous clicks cannot leave it waiting solely because an initial message arrived before the holder existed. **Never** use Web Locks `steal` or `ifAvailable` as a substitute for transfer.
- Only the lock callback may call `audio.play()`. Hold that callback pending through buffering and playing. Release it only after local Pause, source change, media failure, loss of play intent, or teardown has paused the audio and invalidated late promises/events. If lock acquisition times out or errors, abort the request and leave the local audio stopped. On an audio play rejection, stop and release the lock. The existing click report fires only for a confirmed new `playing` attempt.
- Web Lock exclusion, rather than message order, handles simultaneous Play. Whichever frame owns the lock can play; contenders wait or fail closed. A pending request is bounded and cancelable. If a late lock callback runs after its attempt was canceled, it releases immediately without calling `play()`. Foreground and background handlers must use the same path. No timer lease or force-release is allowed: a suspended holder may remain audible, so a second player must not start merely because its heartbeat expired.
- For remote Pause, the idle frame first obtains an observed owner ID/epoch, then sends a request with that target and a unique request ID. Only the matching holder pauses and releases before acknowledging. The requester shows success only on a matching acknowledgment or a separately observed stopped state for that owner. If there is no known or responsive owner, show an unavailable or unconfirmed outcome. An old Pause request must not stop a newer owner or an unrelated new playback attempt. A local Pause stops local audio immediately even if messaging is broken.
- On mounting, request status. The lock holder announces its status on acquisition, confirmed play, Pause, and selection/error transitions and responds to status requests. An announcement includes a bounded station label only. Mark remote state stale after a short interval; staleness changes UI wording, never grants playback rights. `pagehide`/unload best-effort cleanup pauses and releases; normal lock release after frame destruction is expected but must be verified in ChatGPT.

The protocol assumes all participating instances use the same tested origin/storage partition and lock manager. An isolated iframe could acquire a different lock with the same name; runtime code cannot infer an absent peer. Therefore the actual host gate and release verification are mandatory. A platform change that splits the scopes invalidates the support claim and requires reassessment. There is no cross-device guarantee.

## Components, dependencies, CSP, and resource versions

Add a small browser-only coordinator module with injectable lock, channel, clock, and audio interfaces for deterministic tests. Integrate it with `src/player-controller.ts`, `src/player.ts`, and the fixed and discovery HTML resources. Keep discovery and station validation on the server. The MCP server remains sessionless and has no owner registry or remote-control endpoint. Use browser Web Locks, BroadcastChannel, AbortController, and existing TypeScript/build dependencies; add no database, framework, worker, or provider service. Check capability before enabling Play; when unavailable, show that this environment cannot coordinate Dial playback and do not start audio. Remote Pause may be offered only while communication is available, with its acknowledged/unconfirmed semantics.

Version both `ui://dial/...` resource URIs when their delivered HTML/script changes; refresh the ChatGPT connection for host testing. The coordination design adds no fetch/WebSocket endpoint and no `connectDomains`. Keep DIAL-002's finite `resourceDomains` media allowlist and exact stream validation. Verify the **delivered** resource contains the new script and CSP. If the host needs different CSP or sandbox permissions for these APIs, return for review instead of widening policy silently.

## Tests and verification

- Protocol/controller tests with two simulated frames and one genuinely shared fake exclusive lock: simultaneous Play, transfer ordering, old holder pauses before release, delayed/missing/duplicate messages, timed-out lock waiter, late grant after cancel, background-stalled holder, remote Pause acknowledgment/timeout, stale status, source switch, remount, media rejection, and click-report count. Assert that test audio elements never overlap while the lock is shared.
- Build, existing player/discovery tests, MCP Inspector resource/tool smoke checks, and delivered registered HTML/script/CSP assertions. Exercise both fixed and country-discovery resource URIs. These checks prove local behavior and packaging only.
- The capability probe above precedes full feature work. After implementation, independent Verify records actual two-thread ChatGPT audible observations for each PRODUCT acceptance criterion, including a transfer in both directions and Pause issued from the idle frame. Record failures or missing access as FAIL/BLOCKED, not PASS. Browser background scheduling and teardown results must be observed, not inferred from mocks.

## Failure and rollback

On denied/missing lock or channel, protocol mismatch, or failed probe, no coordinated Play starts. On an unresponsive owner, a contender times out and remains silent; an idle remote Pause reports unconfirmed. On audio failure, the holder pauses and releases. If the feature regresses playback, revert the DIAL-003 product commit and restore the reviewed DIAL-002 player/resource versions; no persisted playback data needs migration. Rollback removes the single-playback claim. Foreman controls handoff and any later merge or deployment.
